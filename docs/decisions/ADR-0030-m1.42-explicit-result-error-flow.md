# ADR-0030: M1.42 Explicit Structured Result and Error Flow

Status: Accepted

## Context

S3 already has fixed-layout nominal enums, payload records, explicit `match`,
multi-cell function results, and deterministic IR/Assembly serialization. Host
and collection APIs now need one documented recoverable error vocabulary. A
new generic `Result<T,E>`, exception system, or hidden propagation operator
would cross the roadmap's generics and unwinding boundaries.

## Decision

Recoverable operation outcomes are ordinary nominal enum values declared by the
program. A result contract has one named success variant and one or more named
error variants. Success and error payloads are declared scalar or record
payloads with fixed semantic layout. Error codes are explicit declared values
(a closed enum discriminant or a declared scalar field); error context is
explicit payload data, never an ambient exception or a sentinel convention.

For example:

    record ErrorContext:
        code: tryte
        detail: tryte
    enum ParseResult:
        Ok(value: tryte)
        Err(error: ErrorContext)

    fn parse(flag: trit) -> ParseResult:
        match flag:
            -1:
                return ParseResult.Err(error=ErrorContext(code=7, detail=11))
            0:
                return ParseResult.Ok(value=42)
            1:
                return ParseResult.Ok(value=43)

Callers inspect and propagate results with explicit exhaustive `match`. A
result payload cannot be used as a scalar without matching/extracting its
declared payload, and there is no implicit propagation or unchecked unwrap
syntax. A function propagates an error by returning the matching error variant
explicitly.

## Failure boundary

Recoverable domain failures are result values. Violations of language or
runtime invariants remain deterministic traps or semantic diagnostics:
bounds, overflow, uninitialized access, invalid borrow/use-after-move,
allocation-limit violations, and malformed artifacts are not converted into
ambiguous result sentinels. This preserves the existing safety boundary and
keeps programmer errors distinct from expected operation failure.

## Representation and ABI

The semantic enum layout is the single source of truth: tag cell zero,
payload leaves in declaration order, fixed total width, and deterministic
inactive cells. Nested record payloads are scalarized depth-first. IR and
Assembly use the existing multi-cell result groups and serialization versions.
Native x86-64 uses the existing aggregate result ABI; M1.42 adds no hidden
return pointer convention, no exception table, and no stack unwinding.

## Alternatives

| Option | Safety | Determinism | Roadmap fit | Decision |
| --- | ---: | ---: | ---: | --- |
| A. Nominal payload enums plus explicit match | 5 | 5 | 5 | Selected |
| B. Generic `Result<T,E>` and `?` | 4 | 5 | 1 | Rejected: generics and implicit flow |
| C. Exceptions/unwinding | 2 | 2 | 1 | Rejected: hidden control flow and lifetime cost |
| D. Sentinel/status-only scalars | 2 | 4 | 3 | Rejected: loses typed payload/context |

## Boundary

M1.42 closes the result/error vocabulary and its hosted, IR, Assembly, native,
and differential contract. M1.43 owns scoped host resources and capability
enforcement; it must return its recoverable failures through this contract.
M1.42 does not add generic parameters, reflection, exceptions, unwinding,
implicit propagation, or a second aggregate representation.
