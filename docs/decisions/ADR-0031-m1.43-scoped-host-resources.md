# ADR-0031: M1.43 Scoped Host Resources and Capability Enforcement

Status: Accepted

## Context

M1.36 provides an injectable host-service registry, but the source language
had no typed resource handle, explicit authority, or deterministic cleanup
boundary. Files, processes, sockets, and foreign buffers must not become
ambient compiler capabilities.

## Decision

M1.43 defines two closed source types:

- host_capability;
- resource_handle.

The source boundary exposes only these explicit operations:

- host_capability_grant(i64);
- resource_open(host_capability);
- resource_is_open(&resource_handle);
- resource_kind(&resource_handle);
- resource_invoke(&resource_handle, i64);
- resource_close(&mut resource_handle).

The Python host boundary uses ResourceRegistry, CapabilityToken, ResourceHandle,
ResourceProvider, and ResourceScope. A capability is bound to one registry
authority. Handles carry a private slot and generation; they cannot be
transferred to another registry. A scope closes live handles in reverse
opening order and preserves the first cleanup error.

The source and native fixture providers accept only the closed kind IDs 1..3,
corresponding to file, process, and socket. The native fixture has three
deterministic slots, monotonically increasing per-slot generations, and zero
as the invalid/closed handle value. The provider performs no real filesystem,
process, or socket access. Real providers must be registered at an embedding
boundary and granted explicitly.

## Representation and safety

The language types are nominal and closed even though the current IR and
native representation is one i64 cell. The semantic signatures prevent
arithmetic or arbitrary construction through the source type names. References
to the handle use the existing reference provenance and mutability rules.
Native i64 memory uses the existing 8-byte numeric storage path; no tryte
range check is applied to an i64 cell.

is_open returns a trit. close invalidates the owner cell in the source fixture
and removes the native slot. Use-after-close, double-close, capability denial,
and capacity exhaustion are deterministic resource boundary failures, not
sentinel values. Recoverable provider result payloads remain ordinary explicit
result values under ADR-0030; this milestone does not introduce exceptions,
implicit propagation, or generic result syntax.

## Alternatives

| Option | Safety | Determinism | Roadmap fit | Decision |
| --- | ---: | ---: | ---: | --- |
| A. Explicit opaque handles and registry capabilities | 5 | 5 | 5 | Selected |
| B. Ambient file/process/socket builtins | 1 | 2 | 1 | Rejected |
| C. Raw source integer descriptors | 2 | 2 | 2 | Rejected |
| D. Garbage collection or implicit RAII | 3 | 2 | 1 | Rejected |

## Boundary

M1.43 closes the scoped capability and lifetime boundary with hosted fake
providers and a Linux x86-64 bounded fixture. It does not claim POSIX resource
coverage, garbage collection, threads, unrestricted OS access, or a complete
external provider catalog. M1.44 owns the layered standard-library surface.
