# S3 1.0 Final Stabilization and Publication Gate

Status: **architecture / release policy only**. This document does not publish a release.

## Why this is the active track

`main` already contains the production line that produced S3 `v1.0.0-rc2`. The RC2 release targets commit `db5f4bf10e2066f52bf144d23e6f7db56154e298` and records a clean new-source T4 result: 392 selected, 392 passed, 0 failed, 0 timed out.

A stable `v1.0.0` release does not yet exist. The latest non-prerelease remains `v0.7.0`, while `pyproject.toml` still identifies the `s3-bootstrap` distribution as `0.7.0`.

Accordingly, the next normal project track is not another feature train. It is a bounded **1.0 final stabilization and publication gate**.

Full compiler self-hosting is independent of this gate and remains deferred research. Self-host status must not block S3 1.0.

## Release invariants

```text
ACTIVE_TRACK=S3_1_0_FINAL_STABILIZATION
FEATURE_FREEZE=YES
SELFHOST_BLOCKS_RELEASE=NO
REFERENCE_COMPILER=PYTHON
STABLE_V1_0_RELEASED=NO
AUTO_TAG=NO
AUTO_RELEASE=NO
AUTO_PYPI_PUBLISH=NO
```

The release line is bugfix/correctness/security/reproducibility/documentation/packaging only. Any new language/runtime capability belongs after the stable-release decision.

## F0 — provenance and source freeze

Use the exact current `main` as the planning base. Treat the RC2 merge commit as the last known production certification anchor unless an audit proves a later production change.

Before implementation or release certification:

1. record current `main` SHA;
2. compare RC2 source to current `main`;
3. classify every delta as production, tests, tooling, or documentation;
4. define the exact final source candidate;
5. reject accidental inclusion of self-host development trains or unrelated feature branches.

If production source changes after candidate freeze, inherited RC2 evidence is no longer sufficient and impact recertification is required.

## F1 — version surface closure

The project currently has intentionally independent version surfaces. Before stable 1.0 publication, audit each one explicitly:

- GitHub release/tag version;
- Python distribution version in `pyproject.toml`;
- source syntax version;
- IR schema version;
- S3 Assembly schema version;
- diagnostic schema version;
- package/toolchain manifest versions where applicable.

Recommended stable-release policy:

- tag/release: `v1.0.0`;
- Python distribution: `s3-bootstrap 1.0.0`;
- syntax/IR/Assembly/diagnostic schema versions remain unchanged unless their contracts actually change.

A package version bump is not permission to change language or artifact semantics.

## F2 — feature freeze

Until the stable 1.0 decision:

Allowed changes:

- correctness fixes;
- security fixes;
- deterministic/reproducibility fixes;
- packaging/install fixes;
- release documentation;
- bounded CI/test-harness fixes where they do not weaken correctness gates.

Not allowed on the stabilization line:

- new language features;
- new runtime capability families;
- new optimizer transformations without a release blocker justification;
- new self-host implementation generation;
- promotion of experimental/self-host candidates to default;
- unrelated architecture rewrites.

## F3 — support and claim matrix

Before publication, produce one release claim matrix that separates implementation from certification.

At minimum classify:

| Surface | Required release treatment |
|---|---|
| Python reference compiler | default/reference path |
| Linux x86-64 native | claim only within certified contracts |
| Windows hosted compiler | claim only from current evidence |
| Windows native/PE | do not promote beyond certified evidence |
| Linux AArch64 | structural vs runtime certification kept distinct |
| macOS ARM64 | structural vs runtime certification kept distinct |
| FFI | only the certified bounded surface |
| TLS / crypto | fail closed when vetted providers are unavailable |
| registry / supply chain | deterministic and fail closed |
| performance | characterization unless native comparative evidence exists |
| full compiler self-host | deferred; not a 1.0 gate |

No structural evidence may be rewritten as runtime certification.

## F4 — packaging, installation and reproducibility

For the exact final candidate:

1. build wheel and sdist;
2. inspect metadata and version consistency;
3. install into a clean virtual environment;
4. run `s3 --help` and bounded CLI smoke checks;
5. compile/run representative official examples through the supported paths;
6. rebuild release artifacts independently and compare hashes where the repository's reproducibility contract requires identity;
7. verify LICENSE and included-file inventory.

Publishing to PyPI or another package registry is a separate explicit action and is not authorized by this document.

## F5 — security and supply-chain gate

The final candidate must retain fail-closed behavior for security-sensitive boundaries.

Required review families:

- secret/token audit;
- license consistency;
- archive traversal/link rejection;
- package/registry checksum identity;
- signed-index/trust-policy behavior where supported;
- TLS secure defaults and hostname/certificate verification;
- no insecure provider fallback;
- malformed input/adversarial frontend regression coverage.

## F6 — certification ladder

Certification follows the repository's existing evidence-first policy.

1. focused impact tests during any repair;
2. T0/T1/T2/T3 or the current equivalent gates required by the impact map;
3. Linux x86-64 native/focused matrix when the required environment is available;
4. packaging/install/reproducibility gates;
5. security/supply-chain gate;
6. **exactly one final full-lineage T4** on the frozen release candidate.

The final T4 is confirmation, not a debugging loop.

If it fails or times out:

- persist the raw result;
- classify the failure factually;
- do not rerun simply to obtain green output;
- repair only if justified;
- any source repair creates a new candidate and requires the appropriate recertification before another explicitly authorized final T4.

## F7 — publication boundary

Only after all required gates close may the project become eligible for stable publication.

Publication actions are separate explicit decisions:

1. merge the release candidate if needed;
2. create annotated tag `v1.0.0`;
3. create GitHub Release `S3 v1.0.0`;
4. optionally publish Python artifacts in a separately authorized step.

No architecture or planning PR may automatically perform these actions.

## Existing post-RC development trains

Review/development branches after the RC line, including self-hosting/Gen3 trains, remain outside this stable-release line unless separately promoted by an explicit decision.

Open review debt for those trains is not silently imported into 1.0. Conversely, no such train may be merged merely because the stable release gate exists.

## After stable 1.0

The normal policy becomes:

- `1.0.x`: correctness, security, compatibility and packaging fixes;
- `1.1` planning: begins only after stable-release soak/review and a separate roadmap decision;
- self-hosting: remains a separate design-first research track governed by `docs/selfhost/REENTRY_CRITERIA.md` once that policy lands.

## Success state

The stabilization campaign may ultimately report:

```text

FULL_LINEAGE_T4=PASS

STABLE_RELEASE_AUTHORIZATION=PENDING_HUMAN_DECISION
```
