# S3 1.1 — Reliability & Maintenance

Status: **active — R0 contract freeze**.

Stable base: `v1.0.0` (`7b3c4a56599fc545b30d81ed2956399a31de0223`).

## Goal

S3 1.1 strengthens the reliability of the existing 1.0 language/toolchain before adding another broad capability family. The central deliverable is a deterministic Reliability Lab v2 that can discover, preserve, reproduce, and minimize compiler failures without weakening existing certification boundaries.

This track is intentionally maintenance-first. It does not require a source syntax, IR, Assembly, diagnostic-schema, or package-format bump unless a real defect forces a separately reviewed compatibility decision.

## Why this comes first

The 1.0 compiler line is already broad: frontend, semantics, typed IR, verifier, O0/O1, Assembly, hosted execution, Linux x86-64 native execution, modules, composites, references, networking/FFI/tooling surfaces, and a large certification suite.

The next highest-value step is therefore not more breadth. It is increasing the probability that unexpected feature compositions and malformed inputs fail deterministically, minimally, and reproducibly.

## Non-goals

S3 1.1 does not automatically include:

- full compiler self-hosting or Stage1 V4;
- Gen3/self-host train promotion;
- Quantum, Accelerator, Embedded, or Agent Memory experiments;
- a new backend or widened platform-support claim;
- generics, mature concurrency, JIT, GC, or raw pointers;
- PyPI publication;
- performance claims from structural optimization evidence alone.

Those remain separate decisions.

## Reliability Lab v2 requirements

### 1. Process isolation

Every generated case that can compile or execute runs in an isolated subprocess or equivalent killable process boundary. A timeout must be enforced externally; measuring elapsed time only after an in-process call returns is not a valid watchdog.

R0 freezes the exact canonical outcome set in
[`spec/reliability/R0_CONTRACT.md`](../../spec/reliability/R0_CONTRACT.md):

```text
PASS
EXPECTED_REJECTION
UNEXPECTED_REJECTION
UNEXPECTED_ACCEPT
MISCOMPILE
CRASH
TIMEOUT
NONDETERMINISM
RESOURCE_LIMIT
HARNESS_ERROR
```

### 2. Deterministic generation

Each case is reproducible from explicit metadata:

```text
campaign_id
seed
generator_version
source_sha256
mode
compiler_head
configuration
```

The same seed and generator version must produce identical source bytes.

### 3. Grammar-aware valid corpus

The valid generator should expand beyond tiny scalar templates and cover representative 1.0 compositions, including where practical:

- ternary and machine numeric types;
- functions/calls/recursion;
- loops and `match`;
- arrays and bounds-sensitive access;
- records/enums;
- modules/imports;
- references and mutability;
- O0/O1 paths;
- hosted execution;
- Linux x86-64 native execution in a bounded certified shard.

Coverage is measured explicitly; generated breadth must not be inferred from case count alone.

### 4. Malformed/adversarial corpus

Malformed generation and bounded mutation should exercise parser, semantic, verifier, artifact, and selected trust/input boundaries without assuming that every malformed input must fail in the same phase.

### 5. Differential oracles

At minimum, valid executable cases should compare applicable execution paths:

```text
hosted O0 <-> hosted O1
hosted <-> native Linux x86-64   (certified bounded shard)
```

Additional comparisons may be added only when their semantics and environment are explicit.

### 6. Replay

Every non-PASS result must emit a replay bundle containing enough information to reproduce the exact case against the recorded compiler revision and configuration.

### 7. Minimization

A deterministic minimizer should preserve the failure signature while reducing source size. The minimizer must never silently change failure class.

### 8. Failure signatures

Failure grouping must use stable structured signatures where available rather than raw full exception strings. Diagnostics, exit classes, signal/return code, timeout class, and relevant hashes should contribute to the signature.

### 9. Resource bounds

Campaigns must have explicit limits for source size, case count, per-case wall time, total campaign wall time, output size, and child-process count.

### 10. No hidden promotion

Reliability findings can open correctness issues and drive minimal fixes, but this track does not promote experimental feature branches merely because the harness can exercise them.

## Proposed execution phases

### R0 — contract freeze

Status: **implemented on the R0 contract branch; awaiting integration**.

Frozen artifacts:

- `spec/reliability/R0_CONTRACT.md`;
- `spec/reliability/case-result.schema.json`;
- `spec/reliability/report.schema.json`;
- `spec/reliability/replay.schema.json`;
- `spec/reliability/worker-request.schema.json`;
- `spec/reliability/worker-response.schema.json`;
- `tools/reliability_contract_v2.py`;
- `tests/test_reliability_contract_v2.py`.

The contract freezes report/replay schema IDs, exact failure taxonomy, one-request/one-response worker protocol, parent-side watchdog/kill semantics, SHA-256 based case-seed derivation, canonical JSON rules, replay path rules, and resource limits.

Exit gate: focused schema/contract tests must pass before R1 begins.

### R1 — isolated runner

- implement subprocess worker protocol;
- enforce hard wall timeout and kill semantics;
- capture stdout/stderr/exit/signal deterministically;
- distinguish compiler failure from harness failure.

Exit: adversarial runner tests including real hangs.

### R2 — valid and malformed generation

- introduce grammar-aware valid generators;
- bounded malformed generator/mutator;
- deterministic source hashing and case metadata;
- explicit coverage accounting.

Exit: deterministic generation/replay tests.

### R3 — differential campaigns

- hosted O0/O1 differential;
- bounded Linux x86-64 native shard;
- nondeterminism re-execution policy;
- structured failure persistence.

Exit: local Windows hosted and Linux x86-64 evidence.

### R4 — minimization and triage

- deterministic reducer;
- failure-signature preservation;
- deduplication/grouping;
- machine-readable and Markdown campaign reports.

Exit: seeded synthetic defects reduce to stable reproducers.

### R5 — maintenance closure

- run a bounded clean campaign against the current 1.1 candidate;
- resolve or explicitly classify discovered release-quality defects;
- ensure existing 1.0 regression gates remain green;
- decide whether 1.1 should be released or remain a maintenance checkpoint.

No one-shot full release T4 is authorized merely by reaching R5; release certification remains a separate decision.

## Promotion rule for old Reliability Lab research

PR #238 is preserved as historical prototype evidence. It must **not** be merged wholesale into the post-1.0 line. Reliability Lab v2 starts from current `main` and may reuse ideas, fixtures, or tests only after re-review against the 1.0 contracts.

The prototype's in-process elapsed-time check is specifically not accepted as the v2 timeout implementation because a genuinely hung call cannot be killed from that design.

## Stable baseline protection

For every production correction discovered by the lab:

1. preserve the minimal reproducer;
2. classify root cause;
3. implement the smallest generic fix;
4. add regression coverage;
5. run impact-based gates;
6. keep the `v1.0.0` tag immutable.

## Relationship to future work
